# 新项目起点：可选方向对比

> 配套文档：[项目总览.md](项目总览.md)（功能清单 / 缺陷 / 待完成）
> 归档日期：2026-10-20 ｜ 用途：决定下一个项目从哪个功能开始

---

## 一、先说结论：四个候选方向

按「**不依赖 GPU**」「**依赖最少**」「**能独立交付**」三个维度排序：

| 方向 | 依赖 GPU | 外部依赖 | 已完成度 | 可独立交付 |
|---|---|---|---|---|
| **A. 后处理管线** | ❌ 不需要 | Pillow + numpy | 高（22 个模块） | ✅ 单函数即可用 |
| **B. 动画编辑器** | ❌ 不需要 | Pillow + numpy + OpenCV | 中高（11 个模块） | ✅ 库 + CLI |
| **C. 资产库 / 工作流** | ❌ 不需要 | 无 | 中 | ✅ 服务 |
| **D. AI 生成** | ✅ 必须 | 215G 权重 + diffusers | 中（4 个底座） | ⚠️ 难独立交付 |

**如果目标是「从零把一件事做扎实」，建议 A（后处理管线）**：
纯函数、无状态、无 GPU、单测容易、每个模块都能单独拿出来用/给别人用。

## 二、A. 后处理管线（推荐）

### 现状

22 个模块（`backend/app/pipelines/`），其中 **16 个纯确定性**，不需要模型：

```
matte.py         抠图（三级降级 + despill）
pixelize.py      像素化（全局色板防闪烁）
palette.py       全局调色板（k-means + 固定种子可复现）
sheet.py         精灵表拆分/合成 + 交付前自检
sprite.py        精灵帧规整（共享缩放）
parts.py         部件拆分（几何识别 + 装骨架方案）
layers.py        场景语义分层
resize.py        尺寸规整（含 RPGMaker 三档）
seamless.py      无缝延展（镜像）
tile.py          瓦片接缝修补（偏移-修复法）
refnorm.py       参考图规范化
metrics.py       一致性指标
review.py        审查图
watermark.py     确定性去水印
videoio.py       视频/GIF 拆帧
```

### 已有的好基础

- **算法质量高**：多个管线做了实测驱动的参数选择，不是抄来的默认值
- **测试充分**：`smoke_test.py` 138 条断言全部无需 GPU
- **依赖极简**：Pillow + numpy（+ OpenCV 只用三个函数）

### 已知缺陷

| 缺陷 | 说明 |
|---|---|
| **管线定义双份** | 14 条管线在前端 `PIPELINES` 常量和后端各写一遍，容易不同步 |
| **无用户自定义编排** | 后端 5 条 workflow 是写死的，用户不能自己串管线 |
| **无批处理** | 只能一张张跑，不能「整个文件夹跑一遍抠图 + 像素化」 |
| **抠图仍依赖 rembg** | `rembg` + `onnxruntime` 是 optional 依赖，缺失时退到 GrabCut（效果明显变差） |
| **去水印需掩码** | 无掩码时不破坏性处理，功能等于半残 |
| **参数是魔法数字** | 管线内的容差/阈值散落各处，没有统一的参数对象 |

### 下一步候选

1. **统一参数模型**：每条管线一个显式的 Params 类（可序列化、可预设、可存预设文件）
2. **管线编排**：让用户定义「A → B → C」的链，而不是只能选写死的工作流
3. **批处理模式**：目录进、目录出，参数套用全部
4. **补一条缺失的管线**：QP 棋盘参考图的棋盘格提取（HD-2D / 3D 都需要）
5. **抠图去依赖**：用 ONNX 换个更轻的分割模型，或把 rembg 依赖变成可选路径更干净

### 适合作为新项目起点的理由

- 每个管线是**纯函数**（图片进、结构化结果出），天然可测
- 不需要 GPU，本地跑得动
- 可以做成 **CLI 工具 / 库 / MCP skill** 三种形态，不绑定任何前端
- 参考项目 FrameRonin 和 frameronin-skill 都是这个思路的印证

## 三、B. 动画编辑器

### 现状

11 个模块（`backend/app/anim/`）：

```
model.py      工程数据模型 + 快照
render.py     渲染（3×3 仿射矩阵级联 + FABRIK + 蒙皮 + warp）
export.py     Godot 包（逐帧烘焙）
skin.py       权重（(u,v) 存储 + 手刷）
fx.py         特效笔刷（固定种子幂等）
normals.py    法线 + 金属掩码
gif.py        自研 GIF 编码器
sequence.py   序列帧轨道 + 内容网格检测
tween.py      插帧（曲线求值 + 光流）
diagnose.py   循环接缝诊断
```

### 已有的好基础

- **「数学只有一处实现」贯彻得好**：贝塞尔求值、蒙皮、Godot 矩阵全后端单点实现并烘焙
- **验证充分**：包括「用 Godot 引擎实跑导出包比对」
- **刚做完序列帧轨道 + 循环段 + 插帧 + 接缝诊断**（最近的三个提交）

### 已知缺陷

| 缺陷 | 说明 |
|---|---|
| **前端单文件 2242 行** | `Editor.tsx` 是整个项目最大的文件，改动风险高 |
| **无扭转骨骼** | 四足长躯干要拆很多节骨骼才不扭 |
| **IK 链长限 4 节** | 硬上限 |
| **pole 是静态的** | 不能逐帧换肘向，得建两个 IK 目标 |
| **没有曲线叠加/循环修改器** | 缓动只能单条 |
| **性能是纯 CPU** | 单帧几十毫秒，长工程会卡 |
| **序列帧蒙皮权重整条共用** | 没有「每格单独编辑」 |
| **依赖 Godot 做验证** | CI 上跑不了那段 |

### 下一步候选

1. **拆 Editor.tsx**：状态层 / 渲染层 / 交互层分离
2. **扭转骨骼**：参考 FrameBaker 的 on-character motion editing
3. **曲线叠加 + 循环修改器**
4. **序列帧每格独立权重**

### 适合作为起点的判断

如果目标是「做一个比 FrameBaker 更强的动画编辑器」，这是清晰的方向。但**工作量明显大于 A**，
且需要重新设计前端架构（2242 行的文件不是能直接继承的）。

## 四、C. 资产库 / 工作流

### 现状

- 资产库：本地落盘 + index.json + 双维标签（kind × pipeline）+ sha256 溯源 + 缩略图缓存
- 工作流引擎：5 条写死的多步链，支持单步重跑 + 产物自动传递 + 状态落盘

### 已知缺陷

- 无工程导入导出（只能导出图片包，没有工程 JSON 的导入）
- 无批处理
- 工作流写死，用户不能自定义
- 无协作/无云（这是刻意的设计，LOCAL FIRST）

### 判断

这一块**已经比较完整**，且它的价值依赖于上面两项（管线和编辑器）。
单独做价值不大，适合作为 A 或 B 的配套。

## 五、D. AI 生成（建议放最后）

### 现状

4 个本地底座（215G 权重）：

| 底座 | 用途 | 大小 |
|---|---|---|
| Z-Image-Turbo | 文生图（中文原生） | — |
| Qwen-Image-Edit-2511 | 指令式编辑 | — |
| Qwen-Image-Layered | 图层生成 | 57.7 GB |
| Wan2.2-TI2V-5B | 视频生成 | 31.9 GB |

### 已知缺陷

- 逐帧生成慢（一次一帧，N 帧 = N 次推理）
- 显存吃紧（家族互斥换出，fp8 量化）
- 生成质量不可控（同一 seed 换设备结果不同）
- 环境依赖重（GPU、CUDA、torch、torchao、diffusers）

### 判断

**不适合作为新项目的第一个功能**：
- 依赖最重，环境问题会淹没功能问题
- 测试需要真实 GPU，成本高
- 质量天花板不由代码决定

**但它有一个独立的价值**：把「生成 → 规整」的**接口**定好。
如果新项目要接任何生成能力，建议复用现有的四端点：
`/api/generate`、`/api/generate/ref`、`/api/pipeline/ai_edit` 系。

## 六、我的建议路径

```
第一步（1–2 周）：后处理管线库化
    把 16 条纯确定性管线抽成一个独立的 Python 包
    · 统一参数模型
    · 每个管线一个 CLI 子命令
    · 补齐单测
    产出：能 pip install / 能命令行调用 / 不需要前端和 GPU

第二步：管线编排 + 批处理
    · 用户自定义「A → B → C」链
    · 目录进目录出
    产出：能替代「素材批处理」这个反复出现的日常需求

第三步：接生成
    · 复用现有四端点（或者换成 ImageGen）
    · 生成的产物直接进管线链
    产出：真正的「生成 → 规整 → 交付」闭环

第四步：动画编辑器（如果还需要）
    · 这时手上的管线库已经是现成的输入源
    · 重新设计前端架构，不继承 2242 行的 Editor.tsx
```

## 七、无论选哪个都值得带走的

从归档项目里抄这几条（详见 [项目总览.md §3](项目总览.md)）：

1. **「数学只有一处实现」** —— 预览与导出必须走同一套代码
2. **确定性优先，模型可选** —— 不依赖 GPU 的部分越多，项目越健壮
3. **失败要给可行动的下一步** —— 数字和提示都要能翻译成「所以你现在该做什么」
4. **验证要独立于被验证对象** —— 用注入错误确认检查本身有效
5. **测试数据隔离** —— `PIXELFORGE_DATA_DIR` 指向临时目录，不污染真实数据
